## 3. Observation: stack-cleanup reconciliation (why the mapping holds)

Base `0x442f30` ends `RET 0x8` (observation, `ev_7655...` tail) — pops
both pushed args. Square `0x443290` ends `C3` (observation,
`ev_5843...` bytes `...c3`) — pops only the return address; its `f32`
arg rides in the ONE `PUSH ECX` scratch slot (`0x443397`), reused by
both square calls (`FSTP [ESP]` ×2) and freed once (`ADD ESP,0x4` at
`0x4433c4`). Offsets therefore line up exactly as the pseudocode says:
first arg `p1-p3` (`FLD [ESP+0x30]` / `FSUB [ESP+0x38]` post-`RET-8`
frame), second arg `p2-p4` (`FLD [ESP+0x38]` / `FSUB [ESP+0x40]`
post-call frame); `sq1` stash lands on the dead `p1` slot
(`[ESP+0x34]` pre-`ADD` frame); the three surviving param slots the
comparisons read are `p2`/`p4`/`p6` (`[ESP+0x34/0x3c/0x44]`
post-`ADD` frame). No decompiler parenthesization is trusted beyond
these slot identities — each was hand-checked against the frame above.

## 5. Wiring map (observation, checked against §2 asm + §3 frames)

Slot roles from the xform (`fn_00443450.rs` + arc-xform evidence):
`+12=cx`, `+16=cy`, `+20=r`, `+24=n(i32)`.

- `+4/+8` (via base `0x442f30(p3, p5)`): `lo`/`hi` of
  `(prev_x, new_x)` — observation (same convention as linear/cubic).
- `+0`: vtable `005ce110` — observation.
- `+12` (`in_ECX[3]`): `p1` bit-copy (`MOV EDX,[ESP+0x30]` /
  `MOV [ESI+0xC],EDX`) — observation. `= cx`.
- `+16` (`in_ECX[4]`): `p2` bit-copy — observation. `= cy`.
- `+20` (`in_ECX[5]`): `r = sqrt((p1-p3)^2 + (p2-p4)^2)` — observation:
  each difference `FSTP`-rounded to `f32` before its square call, both
  squares + `FADD` + `FSQRT` in 80-bit `ST0`, single `FSTP m32` store.
  Uses the PREV point only (`p3/p4`); the new point (`p5/p6`) does not
  enter `r` — observation (no claim about intent).
- `+24` (`in_ECX[6]`, `i32`): extremum flag on `p2=cy` — observation,
  asm-ordered (second write wins on ties, so all-equal yields `+1`):
  1. `0` default; `-1` iff `p2<=p4` AND `p2<=p6` under `TEST AH,1`
     (`0x4433dd/0x4433ec`): C0-only test, so unordered (NaN) FAILS the
     pair — ordered-`<=` exactly.
  2. `+1` iff `NOT(p4>p2)` AND `NOT(p6>p2)` under `TEST AH,0x41`
     (`0x443402/0x443411`): C0|C3 test with `JZ`-skip, so unordered
     PASSES — NaN in any leg takes the `+1` arm (e.g. NaN `p2` yields
     `n=+1`, never `-1`, never throw).
  The decompiler's two `<=` spellings are therefore NOT the same
  predicate on NaN (first fails closed, second fails open) — the
  transcription (§6) encodes them as `a<=b` vs `!(a>b)` respectively,
  which match on all ordered inputs AND on NaN.
- `n==0` (strict-interior `cy`, reachable only via ordered inputs):
  `0x406b90(&DAT_005ce0cc, 0)` then `__CxxThrowException_8` — the
  ctor throws instead of returning an element. `0x406b90` internals
  and both `DAT` payloads unmapped (out of scope, §7).

Endpoint identity (checked inference, proved by the test in §6):
at `x = prev_x`, `d = r^2 - (prev_x-cx)^2 = (cy-prev_y)^2` (ordered),
so the xform yields `cy - n*|cy-prev_y| = prev_y` whenever `n = ±1`
is the true extremum sign — i.e. the stored arc reproduces the prev
point exactly (up to `f32` rounding).
